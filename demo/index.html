The assignment

Five required steps. Both implementations cover all five against the real site — nothing is mocked.

Open the B.TECH website.

Search for iphone17.

Select the first result and assert it has an image.

Add it to the cart.

Navigate to the cart.

Two implementations

Robot Framework is the primary submission. Playwright TypeScript is a deliberate second opinion: the same journey written in the idiom of a code-first framework.

Robot Framework

Primary · Browser Library (Playwright engine)

  • Every browser action is a Browser Library keyword, so all 90 steps appear in log.html.
  • Python is reserved for what reads badly as table syntax — and never touches a locator.
  • Locators live in the resource that owns the UI area.
robot/
  config.py            single settings module
  tests/               the scenario
  resources/
    flows/             journey vocabulary
    pages/             route behaviour
    components/        header, cart drawer
    api/               response matchers
    assertions/        image checks
  libraries/           value-only Python

Playwright TypeScript

Secondary · @playwright/test

  • Components take a root Locator, not the page, so each owns its own subtree.
  • Fixtures give every test a fresh context; isolation is framework-managed.
  • test.step blocks make the HTML report read as the journey.
playwright/
  playwright.config.ts
  tests/               the spec
  src/
    app/               BtechApp entry point
    pages/             route objects
    components/        header, card, drawer
    api/               response observers
    support/           image + name helpers
    fixtures/          btech fixture

Separation of concerns

Both implementations use the same four layers. The names differ; the boundaries do not.

TestReads as the business journey. Owns test data (iphone17) and nothing else.
Flow / AppOwns the order of the journey and the state carried between steps, such as the selected product name.
Pages & componentsOwn locators and the behaviour of one route or one UI area. Scoped to a root, so repeated elements cannot collide.
Helpers & API observersPure logic: text normalization, URL parsing, payload assertions, image state. Value in, assertion out — no locators.

Decisions worth a minute

The judgement calls behind the code, and their limits.

Enter is pressed on the input, not the page

An open autocomplete suggestion swallows a page-level keypress and searches for something else. Both implementations target the element.

The image check proves loading, not correctness

complete plus a real intrinsic width catches broken and placeholder images. It cannot catch a valid photo of the wrong product; visual baselines were rejected because the product is selected dynamically from live results.

One API contract is asserted, not mocked

Add-to-cart is observed at the network level — status, payload, and response — because it is the journey's only real mutation. Search and product pages are asserted through the UI.

Startup waits on the regions response

The header renders its delivery city from that call, so the wait is registered before navigation and resolved before the header is asserted.

No retries

Against a live storefront, a visible failure with a trace is more honest than a hidden retry that trains people to ignore red builds.

Results are dynamic, never hardcoded

The first title-relevant result is selected at runtime and its name is carried through every later assertion, so merchandising changes cannot produce a false pass.

Where the pipeline lives

Today the workflow sits in this repository and triggers on its own pushes and pull requests — correct while the tests are the thing being changed. In a real delivery pipeline the trigger usually belongs to the application repository instead: a developer opens a PR, or a release is pushed to staging, and that repository calls this suite as a quality gate.

Nothing in the suite needs to change for that. It takes its target from BEE_TICK_BASE_URL, so the caller points it at whichever environment was just deployed. Two standard ways to wire it:

ApproachHow it worksFits when
workflow_call This workflow is marked reusable; the app repository invokes it as a job and receives pass/fail inline in its own checks. Both repositories are on the same GitHub org — the simplest option, and results block the PR directly.
repository_dispatch The app's pipeline sends an event carrying the deployed URL; this repository runs and reports back via a commit status. The app lives elsewhere (another org, GitLab, Jenkins) or the suite must run on its own schedule too.

Making it callable is a small addition to the trigger block:

on:
  workflow_call:
    inputs:
      base_url:
        type: string
        required: true

jobs:
  robot-e2e:
    env:
      BEE_TICK_BASE_URL: ${{ inputs.base_url }}

And from the application repository, after its deploy job:

e2e:
  needs: deploy-staging
  uses: <owner>/beetick/.github/workflows/e2e.yml@main
  with:
    base_url: https://staging.example.com/en

Run it yourself

No application to deploy, no test data to seed, no credentials.

Robot Framework

cd robot
uv sync --frozen
uv run rfbrowser init chromium
uv run robot --outputdir results --xunit xunit.xml tests

Headed: add --variable HEADLESS:false

Playwright TypeScript

cd playwright
corepack enable
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
pnpm test

Report: pnpm report · Headed: pnpm test:headed

Reports on this page were generated on 14 September 2026 against https://btech.com/en. Because the storefront is live, a later run may select a different product — that is intended, and every assertion is derived from the product chosen at runtime.
