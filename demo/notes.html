Engineering notes

The decisions, and what they cost

Everything on this page is optional reading. It covers the judgement calls behind the two suites, the limits each one accepts, and the things a reviewer would reasonably probe.

Decisions worth a minute

Six choices that shaped the code.

Enter is pressed on the input, not the page

An open autocomplete suggestion swallows a page-level keypress and searches for something else entirely. Both implementations target the element, so the typed term is what gets submitted.

One API contract is asserted, not mocked

Add-to-cart is observed at the network level — status, request payload, and response — because it is the journey's only real mutation. Search and product pages are Next.js server components with no stable business contract, so they are asserted through the UI instead.

Startup waits on the regions response

The header renders its delivery city from that call. The wait is registered before navigation and resolved before the header is asserted; reversing that order makes the city arrive too late and the assertion fail.

Results are dynamic, never hardcoded

The first title-relevant result is selected at runtime and its name carried through every later assertion, so a merchandising change cannot produce a false pass. Matching is normalized, which lets iphone17 match a title rendered as Apple iPhone 17 Pro Max.

No retries

Against a live storefront, a visible failure with a trace is more honest than a hidden retry. Retries train people to ignore red builds. If production instability proves recurrent, the fix is one documented retry — not a blanket three.

Selectors prefer the accessibility tree

Role and name lookups skip the aria-hidden duplicates this site renders — a second "Add to cart" in a sticky bar, a second zoom control. Where a test id exists it is used for structure, with roles inside it.

What the image assertion proves, and what it does not

The requirement says "assert it has an image". That sentence hides a range of rigour, so the suite checks it twice at different depths.

WhereWhat is asserted
Search result card An image element is visible, its alt matches the selected product, and its src is not empty. Presence only — this answers the requirement at the point the assignment names it.
Product page The browser actually fetched and decoded the image: complete is true, intrinsic width is at least 200px, and the source comes from the product media CDN.

A failed fetch leaves complete true with naturalWidth at zero, so those two together catch the broken-image case that a visibility check misses entirely. The width floor rejects tracking pixels and blur-up placeholders that were never swapped for the real image, and the source check rejects fallback art served from elsewhere.

The limit

None of this proves the image looks correct. A valid, fully decoded photograph of the wrong product would pass, and so would a correct image hidden behind an overlay. Catching those needs pixel comparison.

Why visual regression was rejected

Not squeamishness — it is a property of this suite. The test deliberately selects a dynamic product: whichever live result matches the search term that day. Screenshot baselines require a fixed subject, and product photography on a public storefront changes without notice. Baselines here would fail on merchandising updates rather than on defects, which teaches people to ignore failures. Visual regression earns its place against a pinned fixture environment or a component library, not a production journey that picks its own subject.

Browser lifecycle

Every test runs in a fresh browser context, so cart and session state cannot leak between runs. The two frameworks arrive there differently.

ImplementationHow isolation happens
Robot Framework Explicit: Test Setup  Open Fresh B.TECH Browser and Test Teardown  Close B.TECH Browser. The teardown also captures a full-page screenshot when the test failed.
Playwright Framework-managed: the built-in page fixture creates a context per test and closes it afterwards, so the spec contains no explicit open or close. Adding them would break the failure hook that reads page.url(), and would tear down the worker-scoped browser shared with later tests.

A portability bug CI caught

Worth recording because it could never have failed on the development machine.

The Robot suite originally set Test Timeout  60s. It passed locally on Windows every time, and failed on the very first Linux CI run with ValueError: signal only works in main thread of the main interpreter.

The chain, confirmed in the installed sources rather than guessed:

Robot picks a runnerrunning/timeouts/runner.py selects WindowsRunner on Windows and PosixRunner everywhere else.
POSIX uses signalsPosixRunner arms the timeout with signal.setitimer(ITIMER_REAL) and SIGALRM, which only work on the main thread.
Promises use threadsBrowser Library runs Promise To keywords on a ThreadPoolExecutor, so the timeout is armed off the main thread and raises.

The timeout was removed and the reason recorded in the suite file so nobody re-adds it. Coverage is not lost: every wait is already bounded by its own ceiling in config.py, and the CI job caps at ten minutes. The wider lesson is that a suite which only ever runs on one operating system has an untested dimension — CI on Linux was the first thing to exercise it.

Where the pipeline belongs

As written, the workflow lives in this repository and triggers on its own pushes — correct while the tests are the thing being changed. In a real delivery pipeline the trigger usually belongs to the application repository instead: a developer opens a pull request, or a release lands on staging, and that repository runs this suite as a quality gate.

Nothing in the suite changes for that. It takes its target from BEE_TICK_BASE_URL, so the caller points it at whichever environment was just deployed.

ApproachHow it worksFits when
workflow_call This workflow is marked reusable; the application repository invokes it as a job and receives pass/fail inline in its own checks. Both repositories sit in the same GitHub organisation. Simplest, and results block the pull request directly.
repository_dispatch The application's pipeline sends an event carrying the deployed URL; this repository runs and reports back through a commit status. The application lives elsewhere — another organisation, GitLab, Jenkins — or the suite also runs on its own schedule.

Making it callable is a small addition to the trigger block:

on:
  workflow_call:
    inputs:
      base_url:
        type: string
        required: true

jobs:
  robot-e2e:
    env:
      BEE_TICK_BASE_URL: ${{ inputs.base_url }}

And from the application repository, after its deploy job:

e2e:
  needs: deploy-staging
  uses: MohamedRaslan/beetick/.github/workflows/e2e.yml@main
  with:
    base_url: https://staging.example.com/en

What I would do next

Deliberately out of scope for a single-scenario assignment, in the order I would add them.

More of the journey, not more frameworks

Cart quantity changes, removal, and the empty-cart state are the obvious next scenarios. They reuse every component already built.

A pinned environment for visual checks

Once a staging environment with fixed catalogue data exists, screenshot baselines become meaningful and the image assertion's blind spot closes.

Watch artifact size

The published demo includes HTML reports, traces, and videos. Worth trimming retained media or splitting old history once the suite grows.

Cross-browser on a schedule

Chromium covers the journey today. Firefox and WebKit belong on a nightly run rather than in the pull-request path, where they would triple the feedback time.
